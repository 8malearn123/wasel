# ملفات قاعدة البيانات المعلّقة — الترتيب والأثر

آخر فحص: 2026-10-27، قراءة فقط من قاعدة الإنتاج.

## السبب الجذري لأخطاء 404

كل جداول ودوال الملفات من `20261004090000` فصاعدًا **غير موجودة** في قاعدة الإنتاج:

| ما فُحص | النتيجة |
|---|---|
| `subscription_events`، `login_code_attempts`، `product_media`، `roles`، `permissions`، `employees`، `products_v` | `PGRST205` — الجدول غير موجود |
| `my_permissions`، `get_subscription_state`، `wholesale_parties`، `wholesale_listing_items`، `has_permission`، `merchant_subscription_active`، `can_supply_wholesale` | `PGRST202` — الدالة غير موجودة |
| `get_user_merchant_id`، `is_platform_admin` (موجودة من قبل — عيّنة ضابطة) | 200 |

أسماء الاستدعاء في التطبيق تطابق أسماء الدوال في الملفات حرفيًا، وخطأ الصلاحيات كان سيرجع 401/42501 لا 404. السبب: **الملفات لم تُطبَّق** — لا يوجد في المشروع ما يطبّقها تلقائيًا.

أثر جانبي: تفعيل الاشتراك بكود (`redeem_activation_code`) وطلب تغيير الباقة (`request_plan_change`) يستدعيهما التطبيق، وهما غير موجودين أيضًا.

## الترتيب وما يفعله كل ملف

يُطبَّق كل ملف في عملية مستقلة (transaction): إن فشل لا يتغير منه شيء. لا يحذف أي ملف جدولًا أو عمودًا أو صفًا.

## التطبيق (بعد موافقة المالك)

1. أضف السر `SUPABASE_DB_URL` في GitHub → Settings → Secrets and variables → Actions:
   Supabase → Project Settings → Database → Connection string → **Session pooler** (مع كلمة المرور).
   لا يُكتب في أي ملف، وGitHub يخفيه من السجلات.
2. Actions → «Apply database migrations» → `check`: يعرض الملفات الناقصة، ويطبّقها تجريبيًا على نسخة من هيكل الإنتاج، ويطبع الصفوف التي سيعدّلها الملف 12. لا يغيّر شيئًا.
3. بعد مراجعة النتيجة: `apply`. يمكن التطبيق على دفعات بحقل `up_to` (مثلًا `20261004100200` يطبّق 1–6 فقط).
4. يفحص التشغيل الدوال الثلاث بعد التطبيق ويفشل إن بقيت 404. بعدها تُشغَّل اختبارات الأدوار (`e2e-roles.yml`) وتُزال البدائل المؤقتة من التطبيق.
